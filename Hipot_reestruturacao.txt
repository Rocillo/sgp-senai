# Relatório técnico de integração SGP e HIPOT

## Resumo executivo

A inspeção direta dos dois ZIPs mostra que você já tem **duas metades do sistema**: o **SGP** como núcleo web em Flask, com módulo de produção, painel, rastreabilidade e um esqueleto de integração HiPot; e o **HIPOT** como aplicação desktop em Python/PySide6, conectada à porta serial, com banco SQLite local e histórico de ensaios. O melhor uso das **80 horas do SENAI** não é reescrever tudo do desktop para navegador agora. O melhor retorno é **transformar o HIPOT em um agente fino de coleta/sincronização para o SGP**, deixando o **SGP como sistema central** e o **agente Windows** responsável apenas por serial, fila offline e envio confiável. Isso reduz risco, respeita a realidade do hardware na bancada e aproveita o que já existe em ambos os projetos. Essa direção é coerente com a arquitetura modular do Flask por application factory e blueprints, com o uso formal de migrações via Flask-Migrate/Alembic, e com o empacotamento do cliente desktop via PyInstaller/Qt for Python. citeturn6view1turn6view2turn6view9turn6view3turn6view4turn6view5

O ponto mais crítico encontrado é que a **integração automática atual do SGP para HiPot está incompleta e inconsistente**. O SGP já tem rotas e serviço de HiPot, mas o caminho automático hoje passa por um script PowerShell separado e por um endpoint `/producao/gp/hipot/api/result` que, pelo código atual, **atualiza ordem/etapa, mas não grava as medições completas em `gp_hipot_run`**; além disso, há um **erro de contrato de retorno** entre rota e serviço, que tende a produzir resposta HTTP de erro mesmo após commit. Em paralelo, a aplicação desktop HIPOT **lê serial e grava rastreabilidade local**, mas **não sincroniza com o SGP**. Resultado: hoje você tem UI e banco local de um lado, e fluxo/kanban/rastreabilidade web do outro, mas ainda não tem um fluxo único, confiável e auditável de ponta a ponta.

Em termos práticos, eu recomendaria que as 80 horas fossem usadas para quatro entregas centrais: **padronizar a API canônica de ingestão HiPot**, **sincronizar o HIPOT desktop com fila offline**, **persistir as corridas HiPot de forma estruturada no SGP**, e **fechar o ciclo no painel/rastreabilidade do SGP**. O restante das horas deve cobrir migrações, testes, empacotamento e rollback. Isso é factível dentro de 80 horas. Já uma migração total do desktop para uma interface web pura, mantendo a robustez de porta serial em bancada, é uma aposta mais arriscada para esse orçamento e prazo.

A análise abaixo foi feita por inspeção direta dos ZIPs fornecidos nesta sessão.

**Visão geral**  
Projeto pequeno, objetivo e concentrado em uma aplicação desktop GUI. O entry point é `main.py`. O runtime observado é um **cliente PySide6** que abre uma janela, usa uma `QThread` para leitura serial e grava resultados em `hipot.db` local.

**Resumo funcional do HIPOT**

- **Leitura física**: porta serial hardcoded em `COM3`, `9600`.
- **Processo operacional**: o operador precisa informar o número de série antes do teste.
- **Persistência**: tabela local `testes_hipot` em `hipot.db`.
- **Modelo de dados atual**: grava `data_hora`, `numero_serie`, `operador`, `resultado`, `relatorio`, `porta_com`, `baudrate`.
- **Histórico local**: existe tela de consulta, filtro por data/status/S/N.
- **Empacotamento**: existem dois `.spec`; portanto, há intenção clara de build como EXE com PyInstaller. O PyInstaller suporta build a partir de `.spec`, e o Qt for Python documenta compatibilidade com PyInstaller para aplicações PySide6. citeturn6view3turn6view4turn6view5

**Compatibilidade e notas**

- O acesso serial usa `pyserial`, que suporta Windows/COM e fornece ferramentas como listagem de portas e `miniterm`. citeturn7view0turn7view1turn6view7

**Manifestos encontrados**
- `requirements.txt`
- `runtime.txt = python-3.12.8`
- `Procfile = web: gunicorn run:app`

**Observação crítica**

**Dependências usadas no código mas ausentes do manifesto**

**Compatibilidade e notas**

- O projeto usa Flask-Migrate/Alembic, que é o caminho correto para schema evolutivo; mas nem todo o schema real está refletido nas migrações, especialmente o ecossistema HiPot. citeturn6view9

- A execução de auditoria de vulnerabilidades não foi feita pacote a pacote nesta análise; o caminho mínimo recomendado é adicionar `pip-audit` no processo. citeturn6view15

### Modelo de execução do HIPOT

**Conclusão sobre o runtime atual**
- **Não é serviço/daemon**.
- **Não é coletor HTTP nativo**.
- **É uma aplicação desktop GUI** com PySide6.
- **Há empacotamento pretendido em EXE** via PyInstaller (`.spec`).
- **A automação HTTP existente não está no HIPOT desktop**; ela está em um **script PowerShell separado dentro do SGP**.

**Detecção objetiva encontrada no ZIP**
- `main.py` abre `QApplication`.
- `gui.py` instancia `HipotWindow`.
- `serial_worker.py` roda em `QThread` e chama `serial.Serial`.
- `.spec` PyInstaller presentes.
- Nenhum arquivo de serviço Windows, tarefa agendada ou agente HTTP embutido foi encontrado no ZIP do HIPOT.

**Assunção explícita**
- Assumo, com alta confiança, que o HIPOT hoje roda **como script Python local ou EXE PyInstaller gerado desses `.spec`**, operado manualmente na bancada.

**Passos de detecção se você quiser validar em 2 minutos**
```bash
python -m serial.tools.list_ports
pyinstaller --noconfirm --clean Hipot_Pneumark_v2.spec
```

Se o build gerar `dist/Hipot_Pneumark_v2.exe`, o runtime empacotado está confirmado. O PyInstaller documenta build por `.spec`, e o Qt for Python documenta suporte a PyInstaller para apps PySide6. citeturn6view5turn6view3turn6view4turn7view1

## Integração e riscos

### O que já existe de integração

O módulo HiPot do SGP **já existe**, mas está em estado híbrido: parte manual, parte placeholder e parte automática incompleta. Há rotas para:
- edição de perfil HiPot;
- execução manual;
- submissão via modal do painel;
- endpoint de resultado para coletor;
- rastreabilidade/timeline;
- atualização de `gp_work_order` e `gp_work_stage`.

Também existe um script PowerShell `collector_hipot_post.ps1` que:
- abre porta serial;
- parseia a etiqueta EPL;
- resolve serial;
- faz POST para `/producao/gp/hipot/api/result`.

Ou seja: o SGP **já foi preparado para receber HiPot**, mas a espinha dorsal ainda não está fechada.

### Matriz de integração

| Fluxo | Situação atual | Problema | Adaptador/ação necessária |
|---|---|---|---|
| Equipamento HiPot → HIPOT desktop | Funciona via serial, porta hardcoded `COM3/9600` | Configuração fixa; sem reconexão robusta; sem sync web | Tela/config local + retry/reconnect + fila offline |
| HIPOT desktop → `hipot.db` | Funciona | Banco local isolado; sem envio ao SGP | Criar sincronização HTTP assíncrona |
| Equipamento/PowerShell → SGP `/api/result` | Existe | Endpoint atual não grava corrida completa em `gp_hipot_run`; ignora medições estruturadas | Substituir por API canônica de ingestão |
| SGP `/api/result` → `gp_work_order`/`gp_work_stage` | Parcial | Há bug de contrato entre rota e serviço; cliente pode receber erro após commit | Corrigir assinatura/retorno e testes |
| SGP manual (`/api/save`) → `gp_hipot_run` | Existe | Duplicação de lógica; commit transacional inconsistente | Centralizar em um service único |
| SGP painel (`/api/painel-submit-result`) | Existe | Fluxo parcial; sem unificação com coletor automático | Reusar mesma API canônica |
| SGP rastreabilidade → `gp_hipot_run` | Existe leitura | Tabela está vazia no snapshot analisado e alguns campos de tempo não são preenchidos | Garantir ingestão automática e timestamps |
| HIPOT histórico local → SGP | Não existe | Histórico antigo preso no SQLite local | Importador/replay com deduplicação |

### Achados críticos

#### Falha estrutural da integração automática HiPot

O caminho automático atual do SGP usa `collector_hipot_post.ps1` → `/producao/gp/hipot/api/result`, mas o endpoint atual:
- **não cria `GPHipotRun`**;
- **não persiste medições estruturadas** que o coletor já envia;
- **atualiza ordem/etapa, mas deixa a rastreabilidade técnica incompleta**.

Isso é, hoje, o principal gargalo para “virar um sistema só”.

#### Bug de contrato entre rota e serviço

O serviço `aplicar_resultado_hipot()` retorna um **dicionário**, mas a rota `hipot_result_apply()` tenta usar o retorno como se fosse um **objeto com atributos** (`order.serial`, `order.hipot_status`, etc.).  
Efeito provável:
- o serviço faz commit;
- em seguida a rota falha;
- o cliente recebe erro;
- o coletor pode interpretar como falha e repetir tentativas.

Isso precisa entrar no pacote da hora zero.

#### Falta de autenticação na API de coleta

As rotas HiPot analisadas não estão protegidas por `@login_required`, e o PowerShell até prevê um `X-Admin-PIN`, mas a rota não valida esse cabeçalho. O Flask-Login é adequado para sessão web de usuário humano, mas para máquina/coletor você precisa de autenticação própria de API. citeturn6view8

#### Schema real diferente do schema versionado

O banco analisado contém `gp_hipot_run`, mas **não há migração Alembic correspondente criando essa tabela** nos diretórios de migração observados. Isso significa que o schema atual depende de `create_all`, debug routes, ou ajustes manuais. Flask-Migrate/Alembic existe justamente para evitar esse desvio. citeturn6view9

#### Dados de snapshot inconsistentes

No `instance/pneumark.db` do ZIP analisado:
- `gp_work_order` está vazio;
- `gp_work_stage` tem 141 linhas órfãs.

Isso não significa necessariamente que sua produção esteja assim, mas significa que o snapshot entregue no ZIP **não serve como fonte confiável de integridade referencial**.

#### Placeholders e inconsistências de UI

- `profile_editor.html` é placeholder.
- `exec_manual.html` ainda se descreve como “Passo 1 — sem salvar”, mas já salva.
- há múltiplos caminhos de gravação HiPot com lógica sobreposta.

#### Risco de segurança e compliance

O ZIP do SGP inclui:
- credenciais em texto puro;
- `req.json` com segredo;
- banco e snapshots;
- backups;
- `venv`;
- `.git`.

Isso precisa ser saneado antes de qualquer trabalho externo.

## Escopo priorizado de 80 horas

### Princípio de priorização

O grande objetivo deve ser: **“o teste ocorre na bancada, o resultado entra no SGP de forma confiável, com fila offline, sem perda de medições, e aparece no painel/rastreabilidade”**.

### Tabela de escopo SENAI

| Tarefa | Horas | Prioridade | Risco | Critério de aceite |
|---|---:|---|---|---|
| API canônica de ingestão HiPot no SGP, corrigindo o endpoint atual e unificando o contrato | 14h | Muito alta | Médio | Um POST com serial + medições + status cria corrida HiPot, atualiza ordem/etapa e responde 200 consistente |
| Migrações Alembic para o domínio HiPot e saneamento de schema | 8h | Muito alta | Médio | Banco limpo sobe do zero com migrações; nada depende de `create_all` ou rota debug |
| Cliente de sincronização no HIPOT desktop com fila offline, retry e config de URL/token | 18h | Muito alta | Alto | Se o servidor cair, o ensaio fica em fila e sincroniza depois sem duplicar |
| Perfil HiPot por modelo no SGP | 10h | Alta | Médio | Usuário configura limites GB/HP por modelo e essas regras passam a ser usadas na validação |
| Integração com painel B5 e rastreabilidade web | 12h | Alta | Médio | Corrida automática aparece no kanban, no detalhe por serial e no histórico técnico |
| Importador de histórico do `hipot.db` local para o SGP | 6h | Média | Baixo | Histórico antigo entra no SGP com deduplicação por serial/data/hash |
| Testes automatizados e fixtures de regressão | 7h | Alta | Médio | Cobertura mínima dos fluxos críticos: ingestão, fila, painel, replay |
| Empacotamento desktop, deploy web, documentação e rollback operacional | 5h | Alta | Baixo | EXE gerado, checklist de deploy validado e rollback documentado |

**Total: 80h**

### Escopo técnico recomendado

#### O que deve entrar nessas 80h

- **Unificar a entrada HiPot** em uma única API de negócio do SGP.
- **Persistir corrida HiPot completa**, não só status final.
- **Aproveitar o HIPOT desktop como agente de bancada**.
- **Dar visibilidade web no SGP**: painel, rastreabilidade, histórico.
- **Criar migração e replay de histórico**.
- **Eliminar dependência de endpoints debug e acoplamentos frágeis**.

#### O que eu não colocaria nessas 80h

- Reescrita completa do HIPOT PySide6 em frontend web.
- Redesign geral do SGP inteiro.
- Refatoração ampla de todos os módulos fora do domínio HiPot.
- Automações secundárias como e-mail/Outlook e relatórios “bonitos” antes de estabilizar ingestão.

| Fluxo de produção | atualização de `gp_work_order`, `gp_work_stage`, B5 | testes de integração | ordem evolui corretamente |
| Offline/retentativa | servidor indisponível e retorno posterior | teste manual + fixture | fila guarda e entrega depois |
| UI web | painel B5, detalhe por serial, histórico HiPot | smoke manual | resultado visível e coerente |
| Hardware | cabo solto, COM errada, reconexão | bancada real | operador recebe feedback e sistema recupera |

### Estratégia de rollback

#### Web SGP
- Tirar **backup do banco antes de cada migração**.
- Publicar com **flag de recurso** para nova ingestão HiPot.
- Se falhar:
  - desabilitar flag;
  - reverter para commit anterior;
  - restaurar snapshot se a migração impactar produção.

#### Desktop HIPOT
- Manter **último EXE estável** guardado.
- Não sobrescrever banco local sem backup.
- Se a sincronização falhar em produção, o agente deve:
  - continuar gravando localmente;
  - enfileirar pendências;
  - permitir rollback para EXE anterior sem perda do `hipot.db`.

### Perguntas abertas e limitações

- O ZIP do HIPOT **não trouxe manifesto de dependências**, então a reprodução exata do ambiente depende de inferência por imports.
- O modo exato de execução em produção do HIPOT (script, EXE manual, inicialização automática) **não aparece configurado no ZIP**; a análise assume script/EXE manual com alta confiança.
- Há uma **diferença de linguagem de modelo** entre o que aparece no histórico HiPot local (`HGF148` no relatório bruto) e os modelos do SGP (`PM2100`, `PM2200`, `PM700`). Para integração, a chave primária deve ser o **serial**, e não o texto do relatório.
- O `instance/pneumark.db` do ZIP contém inconsistências referenciais; trate-o como **snapshot de trabalho**, não como verdade definitiva do ambiente produtivo.
- Se houver exigência de “rodar tudo no navegador” na bancada, isso muda o escopo e aumenta o risco. Na configuração atual, a solução tecnicamente mais segura é **SGP web central + agente Windows de HiPot**.
